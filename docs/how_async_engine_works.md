# How the FeynRL Async Engine Works

A guided tour of FeynRL's overlapped reinforcement-learning engine: what runs where, how rollout data and policy weights move through the system, and where the time goes. Standard ML terminology, no code required.

## 1. The big idea: overlap generation and training

RL fine-tuning of a language model alternates between two very different workloads:

- **Rollout (generation)** — the current policy generates completions for a batch of prompts, and a reward function scores each completion.
- **Training** — the policy is updated with gradient steps computed on those reward-labeled rollouts.

These two workloads want completely different software stacks. Generation is fastest on an inference engine (vLLM) that keeps only the model weights and a KV cache in memory and batches many requests together. Training needs the full optimizer state, gradients, and activations — several times the model's size in memory — and runs under a distributed training framework (DeepSpeed). Neither stack is good at the other's job, so FeynRL gives each its own GPUs.

A fully synchronous engine alternates the two: generate a batch, stop, train on it, stop, generate again. At any moment, half the hardware is idle — the rollout GPUs wait during training and the training GPUs wait during generation.

The async engine instead splits the GPUs into **two dedicated pools that run concurrently**. While the training GPUs run optimizer steps on the previous batch of rollouts, the rollout GPUs are already generating the next one. Once per cycle, the training side synchronizes its updated policy weights to the rollout side, and the loop continues.

The price of this overlap is that training always studies data generated by a slightly older policy — the data is *one step behind*. Section 6 explains why a bounded amount of this staleness is safe, and how the engine both limits it and corrects for it in the loss.

## 2. The components and how data flows

Six pieces make up the pipeline. Prompts and rollout data flow left to right; updated policy weights flow back right to left.

</picture>

**Figure 1.** The pipeline. Green boxes are rollout/generation, indigo boxes are training, the amber band is the weight sync, and gray boxes are queues and storage. Both queues are bounded on purpose: when a queue fills up, the producer side blocks (backpressure) — nothing overflows and nothing is lost.

- **Prompt producer** — a lightweight background thread that endlessly streams prompt batches from the dataloader into the prompt queue. When it reaches the end of the dataset it reshuffles and starts a new pass, so the queue never runs dry at epoch boundaries. Each batch is split into *shards* — one slice per rollout engine — so all engines get an equal share of work. When the queue is full, the producer blocks until space frees up.
- **Rollout engines** — each engine is a vLLM inference server owning one GPU (or a group of GPUs, if the model needs tensor parallelism). An engine continuously pulls a shard of prompts and samples *several completions per prompt* — the group of completions is what group-based advantage estimators like GRPO need to compute a baseline. vLLM's *continuous batching* keeps the GPU saturated: new requests join the running batch as old ones finish, rather than waiting for the whole batch to drain. For every generated token the engine also records the **behavior log-probability** (the probability the generating policy assigned to that token) — the training loss needs it later for off-policy correction. Finally, the engine runs the reward function on each completion and pushes the scored samples to the results queue. Each engine is pipelined: it keeps one shard generating in flight while it post-processes the previous shard, so the GPU never drains between shards.
- **Replay buffer** — the pool of reward-labeled samples awaiting training. Each entry holds the token sequence, its per-token rewards and advantages, the behavior log-probs, and a **policy-version tag** saying which policy generated it (why this matters: section 6). The buffer has a hard capacity derived from the config, so memory can't grow without bound.
- **Training engines** — GPUs holding the full training state: optimizer moments, gradients, and the model weights sharded across all training GPUs with DeepSpeed ZeRO-3 (each GPU permanently stores only a slice of every weight tensor, and slices are gathered on the fly during forward/backward). Every training GPU must receive the same number of mini-batches per step — otherwise their collective operations would deadlock — so batch construction is deliberately kept uniform.
- **Orchestrator** — a single driver process that ties everything together: it moves results from the queue into the buffer, dispatches training steps, tracks policy versions, monitors the health of every component, coordinates the weight sync, and writes checkpoints and metrics.

The two bounded queues are the engine's flow control. If training falls behind, the results queue fills, rollout engines block on their next push, and generation naturally pauses — no special throttling logic needed. If generation falls behind, the trainer simply waits at the start of the next round. Either side can be the bottleneck without anything breaking.

## 3. The training loop: one round, four phases

The engine runs in repeating **rounds**. Each round has four phases, and the key property is that phase 3 executes *while the rollout engines keep generating in the background*.

  <img alt="Flowchart of one round: collect fresh rollouts, evict stale samples and build training batches, train while rollout engines keep generating, then synchronize weights and loop back." src="images/async_engine/fig2_round.svg">
</picture>

**Figure 2.** One round of the engine. Phases 1–2 are quick bookkeeping; phase 3 is the bulk of the compute; phase 4 is the only moment the two GPU pools must coordinate.

### Phase 1 — collect

"A round's worth" means one full pass over the rollout dataset: a fixed number of prompt shards the orchestrator counts as they arrive. In steady state most of this data was already generated during the previous round's training phase — some of it was even collected early, during the previous weight sync, and is credited against this round's target so nothing is waited for twice. The wait is protected by a timeout: if the target count doesn't arrive in time, the engine fails with a diagnosis (rollout too slow, or an engine stuck) rather than hanging silently.

### Phase 2 — evict and batch

First, samples whose policy-version tag falls outside the staleness bound are evicted (section 6). The remaining buffer is then shuffled with a seeded RNG and cut into equal-sized mini-batches, distributed evenly across the training GPUs. The equal sizing is not cosmetic: under ZeRO-3, all training GPUs participate in every collective operation, so an uneven split would leave one GPU waiting forever.

### Phase 3 — train

The training engines run a configurable number of passes over the round's mini-batches, with gradient accumulation inside each pass. Multiple passes squeeze more learning out of each batch of expensive rollouts — and this is safe because the loss is a *clipped* surrogate objective (PPO-family): the clipping stops the policy from drifting arbitrarily far from the data within a round. All the while, the rollout engines keep pulling prompts and generating in the background; their output accumulates in the bounded results queue and replay buffer, ready for the next round. Throughout this phase the orchestrator also polls every component's health, so a crashed engine surfaces within seconds instead of at the end of the round.

### Phase 4 — sync

The policy version increments, and the updated weights are delivered to every rollout engine (section 5 walks through this). One detail: the final round of a run skips the sync — there is no next round to generate for — and instead just drains and collects the remaining in-flight rollouts so the run's statistics are complete.

## 4. Where the time goes

The whole point of two concurrent pools is **overlap**: during the long training phase, the rollout engines are simultaneously generating the next round's data. The timeline below shows one round for each pool, including the intervals where GPUs sit idle — the **bubbles**.

<picture>
  <source media="(prefers-color-scheme: dark)" srcset="images/async_engine/fig3_timeline_dark.svg">
  <img alt="Timeline showing rollout and training GPU activity across one round, with overlap in the middle and idle bubbles during the drain and the weight sync." src="images/async_engine/fig3_timeline.svg">
</picture>

**Figure 3.** One round on the clock (hatched blocks are idle time). The long middle stretch is fully overlapped. Three bubbles remain: a usually-short wait for data at round start (A), the drain while in-flight generations complete before the sync (B), and the weight-broadcast pause itself (C).

- **Bubble A — waiting for data.** At round start the trainer needs a full round of fresh rollouts. In steady state this data was already generated during the previous round, so the wait is short. It only grows when generation throughput is genuinely lower than training throughput (a rollout-bound configuration).
- **Bubble B — the drain.** Before weights can be updated, every rollout engine must finish its in-flight generations — a partially generated sequence cannot switch policy versions midway (see the guarantee in section 5). The drain lasts about as long as the slowest in-flight request, so long completions (high `max_tokens`) mean a longer drain. Nothing generated during the drain is wasted: those samples land in the replay buffer and count toward the next round.
- **Bubble C — the weight broadcast.** Gathering and broadcasting the parameters. Typically seconds; scales with model size, not with generation length.

### Which bubble dominates?

It depends on the workload. With long completions (reasoning-style generation with thousands of tokens per response), bubble B dominates — the slowest in-flight request can take minutes to finish. With short completions and a large model, bubble C's broadcast becomes the visible cost. Bubble A appears only when the GPU split is out of balance: if the rollout pool can't produce a round's worth of data in the time the training pool takes to consume one, the trainer starves. The engine logs a *speed ratio* each round — rollout output produced per round versus one round's demand — precisely so this imbalance is visible: a ratio below 1 means "add rollout GPUs (or generate less)", a ratio above 1 means rollout capacity is more than sufficient and some of its output may age out unused.

## 5. Weight synchronization, step by step

Once per round, the rollout engines' copy of the policy is replaced with the newly-updated one from the training side. This is trickier than it sounds: the training weights are sharded in slices across all training GPUs (ZeRO-3), the rollout copies live inside separate vLLM server processes, and nobody wants to write anything to disk in between. It happens in four steps:

<picture>
  <source media="(prefers-color-scheme: dark)" srcset="images/async_engine/fig4_weight_sync_dark.svg">
  <img alt="Four-step weight sync: stop feeding prompts, drain in-flight generations while the trainer gathers its sharded weights, broadcast parameters GPU-to-GPU over NCCL with validation, then resume generation." src="images/async_engine/fig4_weight_sync.svg">
</picture>

**Figure 4.** The weight sync. Step 2 is the expensive part; step 3 is fast because parameters travel directly between GPUs over the cluster's high-speed interconnect — they never touch disk.

A few details worth knowing:

- **The gather hides inside the drain.** Reassembling the full weights from their ZeRO-3 slices takes time, so the trainer starts it the moment the shutdown signals go out (step 1) and runs it concurrently with the drain (step 2). By the time the last in-flight generation finishes, the weights are usually ready to broadcast.
- **A dedicated communication channel.** The broadcast runs over its own NCCL process group, linking the lead training GPU with every rollout GPU — separate from the group the trainer uses for its own gradient collectives, so the two can never interfere.
- **All-or-nothing per engine.** Each rollout engine counts the parameters it received and compares against the announced total. Any shortfall, or any tensor containing NaN/Inf values, means the engine keeps its previous weights and reports failure — the policy version does not advance on that engine.
- **Failure is graceful where possible.** If the broadcast fails for a recoverable reason, the run continues: rollout engines keep generating with their current (one-step-older) weights, and the next round's sync retries. Only unrecoverable communication failures — or an engine that has stopped responding entirely — abort the run, loudly.

> **One guarantee worth knowing:** because rollout fully drains before the weights are updated, *every trajectory is generated end-to-end by a single policy version* — no sequence starts under one policy and finishes under another. This keeps the behavior log-probabilities and importance ratios in the loss well-defined and the training data easy to reason about.

## 6. Off-policy data and the staleness bound

Here is the subtle consequence of overlap: while training runs, the rollout engines are still generating with the *previous* policy version. By the time those samples are trained on, the policy has already advanced — the data is slightly **off-policy (stale)**.

Why does staleness matter at all? Policy-gradient methods estimate "which actions should become more likely" from the current policy's own behavior. Feed them data from a very different policy and the estimate is biased — the update can push the model in the wrong direction, and training quality degrades quietly. But data from a policy that is only one or two updates old is nearly identical to on-policy data, and with the right correction it is safe to use. The engine exploits exactly this window, in two complementary ways:

- **A staleness bound.** The `max_lag` setting caps how many policy versions old a sample may be and still be trained on. Anything older is evicted from the replay buffer at the start of each round. This is a hard guarantee, independent of timing or luck.
- **Off-policy correction in the loss.** Each sample stores the behavior policy's per-token log-probabilities from generation time. At training time the loss compares them with the current policy's log-probabilities and forms an *importance ratio* per token — intuitively, "how much more (or less) likely would I be to produce this token now?" Tokens the updated policy would rarely produce are down-weighted; tokens it agrees with keep their full weight. The ratio is *clipped* against a fresh reference policy (a decoupled, PPO-style objective), and the staleness weight itself is capped, so even the oldest samples inside the bound can never yank the policy too far in one step.

  <img alt="The replay buffer keeps samples from the current policy version and up to max_lag previous versions; older samples are evicted." src="images/async_engine/fig5_staleness.svg">
</picture>

**Figure 5.** The staleness bound. A larger `max_lag` retains more past data (more sample reuse, but more off-policy); a smaller one keeps training closer to on-policy at the cost of discarding more rollouts.

### Choosing max_lag

Small values (1–2) are the common choice: they keep training close to on-policy while still capturing the full overlap benefit — the data generated during training is at most one version behind by the time it is used. Larger values let the buffer accumulate more history, which increases sample reuse and smooths out fluctuations in generation speed, at the price of a more off-policy gradient that leans harder on the importance-weighting correction. The engine logs the actual staleness of every training batch (maximum, mean, and number of distinct versions present in the buffer), so the effect of the setting is visible in the metrics rather than a matter of faith.

## 7. Safety mechanisms

A large share of the engine's code isn't about throughput at all — it's about making failures loud and harmless instead of silent and corrupting:

- **Heartbeats everywhere.** The prompt producer, the rollout engines, and the orchestrator all log progress every 30 seconds — items produced, items drained, queue depths, buffer size. A stall surfaces in the logs immediately, with enough context to tell *which component* stalled and whether it is starved (waiting for input) or blocked (waiting for space).
- **"Busy" vs. "hung" detection.** Each rollout engine answers health checks on a channel separate from its main workload, so the orchestrator can distinguish an engine that is slow because it is generating long sequences from one that has genuinely deadlocked. A hung engine is reported with its last-progress timestamp instead of being mistaken for a busy one.
- **No partially-updated policies.** If a weight sync delivers an incomplete parameter set, or any tensor contains NaN/Inf values, the rollout engine keeps its previous weights and reports the failure — it will never generate with a corrupted model.
- **No cross-version contamination.** After every weight update, rollout engines invalidate their KV / prefix caches, so cached activations computed under the old weights can never mix into sequences generated by the new ones. If the invalidation itself fails, the engine aborts rather than continue with silently biased rollouts.
- **Timeouts on every wait.** Waiting for data, for training steps, or for the sync all carry deadlines with actionable error messages — naming the likely cause and the settings to adjust — instead of hanging indefinitely.
- **Clean shutdown, no lost work.** Stopping the engines uses per-engine shutdown signals, and every in-flight result is flushed to the buffer before an engine exits — even when the exit is caused by an error. Un-served prompts are re-issued on restart.
- **Sample accounting.** Rollouts that complete during the sync drain are still collected and credited toward the next round's target, so overlapped work is never double-waited or lost.

## 8. Glossary

| Term | Meaning |
| --- | --- |
| Rollout engine | A vLLM inference server owning one GPU (or a tensor-parallel group of GPUs); generates completions and computes rewards. The rollout GPU pool. |
| Training engine | A GPU holding the full training state (DeepSpeed ZeRO-3); computes gradients and runs optimizer steps. |
| Continuous batching | vLLM's scheduling strategy: new requests join the running batch as old ones finish, keeping the GPU saturated instead of waiting for a whole batch to drain. |
| ZeRO-3 | DeepSpeed's memory-sharding mode: every weight tensor is split in slices across all training GPUs and reassembled on the fly when needed. |
| Shard | One rollout engine's slice of a prompt batch; the unit of work flowing through the queues. |
| Round | One full cycle: collect rollouts → multiple optimizer passes → weight sync. |
| Policy version | A counter incremented at every weight sync. Every sample is tagged with the version that generated it. |
| Replay buffer | The pool of reward-labeled rollout samples awaiting training, kept within the staleness bound. |
| Staleness bound (`max_lag`) | The maximum number of policy versions a sample may lag behind and still be used for training. |
| Behavior log-probs | Per-token log-probabilities recorded at generation time; the loss uses them for importance-ratio (off-policy) correction. |
| Importance ratio | Current policy probability divided by behavior policy probability for a token; down-weights tokens the updated policy would no longer produce. |
| Bubble | An interval where some GPUs sit idle waiting on others. |
| Overlap | The interval where generation and training run concurrently — the reason this engine exists. |
| Weight sync | The once-per-round NCCL broadcast of updated policy weights from the trainer to all rollout engines. |
| Drain | Letting all in-flight generations finish (and collecting their results) before the weights are swapped. |
| Shutdown signal | A sentinel placed on the prompt queue (one per engine) that tells a rollout engine to wind down cleanly — often called a poison pill. |
